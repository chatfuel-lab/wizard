Build on your own AI agent platform in one command. Pick the pieces you want, and the wizard
scaffolds a working React app, installs the skills your coding agent needs to
keep building it, and — if you ask it to — deploys it.

```bash
npx @chatfuel/wizard
```

<p align="center">
  <img src="https://raw.githubusercontent.com/chatfuel-lab/wizard/main/docs/images/demo.gif" alt="The wizard, from the first question to a running app" width="760">
</p>

Two things you can build with it:

- **A tool for your own bot** — an inbox, a CRM, a booking calendar, a catalog,
  whatever your team actually needs, on your own data, with your own workflow in
  it instead of somebody else's.
- **A product of your own.** Add the `auth` module and the app becomes
  multi-tenant: anyone can sign up, and their account gets an AI agent of its
  own — as many as they need, in fact — created inside your workspace and running
  on your plan. Your branding, your pricing, your customers — Chatfuel is the
  infrastructure underneath. Deploy it, point a domain at it, and it is a SaaS.
  What it does not come with: sign-up is open to anyone who finds the URL until
  you close it, every account that signs up spends your Chatfuel plan's quota,
  and there is no billing in the box — see
  [what `auth` on a public URL still lets a stranger do](https://github.com/chatfuel-lab/wizard/blob/main/docs/deployment.md#what-auth-on-a-public-url-still-lets-a-stranger-do).

The only prerequisite is **Node 20.18.1 or newer**. The wizard installs the app's
dependencies itself, and offers to install a coding agent (Claude Code or Codex
CLI) if you do not have one.

## What it does

1. Asks which modules you want.
2. Asks for your Chatfuel API token — from
   <https://panel.chatfuel.com/integration/auth/token> — and checks it before
   going any further.
3. Asks which Chatfuel workspace the app should open on. Not which bot — the
   app lists your workspaces and their bots itself, so a bot you create next
   month is in the picker without a re-run.
4. Checks whether that workspace has a plan, and starts one if it has not. A
   workspace with no subscription has no AI: the bot answers nothing, and the
   app you are about to get looks broken for reasons that have nothing to do
   with it. So checkout opens in your browser — it wants a card even for the
   trial — and the wizard waits, with a way out if you would rather come back
   to it later. A trial belongs to the Chatfuel account rather than to a
   workspace, so the second workspace of the same account gets the plain
   checkout instead. `--dry-run` prints what this step would do and opens nothing.
5. Asks what the app is called and, if you have one, for a logo file. Both are
   yours from the first run: the name is the browser tab, the top bar and the
   sign-in screen, and the image becomes the tab icon and the mark beside it.
   Skip either and the app still ships a name and a real logo.
6. Settles the admin password, if you picked the `admin` module. Generated by
   default — it is a secret nobody has to remember — or typed, if you would
   rather. It goes into `.env` and is printed once, and into nothing that gets
   committed: not the handoff, not the agent instructions, not a README.
7. Writes the app and installs its dependencies.
8. Offers to deploy it to Vercel.
9. Offers to put it on GitHub: a repository, a first commit, an `origin`. Like
   the deploy, this one is interactive only — neither happens under `--yes`.
   Before anything is pushed it checks three things, and it is worth knowing
   which: every file about to be committed, by name and by content; every path
   the repository has ever committed, by name; and the contents of the files in
   that history, up to a ceiling — 20,000 files, 1 MB each. Anything past those
   ceilings goes unread and the run says so, with a count, rather than calling
   the history clean. The content checks look for the credentials *this run*
   holds, so somebody else's key in your history is not something they can find.
10. Installs the module skills where your coding agent reads them — `.claude/skills/`
    for Claude Code, `.agents/skills/` for Codex — and writes the instructions file
    that agent reads, so "add a column to the deals table" is a sentence you can
    type rather than a file you have to find.

## Commands

```bash
npx @chatfuel/wizard              # scaffold a new app
npx @chatfuel/wizard --embed      # add the modules to a project you already have
npx @chatfuel/wizard doctor       # what the wizard can see, before it asks anything
npx @chatfuel/wizard update       # bring an app it made up to this wizard's content
npx @chatfuel/wizard auth         # replace the stored Chatfuel token
```

Useful flags: `--dir <path>` (where to write it), `--modules <ids>` (skip the
picker), `--agent <claude|codex>` (which coding agent finishes the setup),
`--workspace <id>`, `--app-name <name>` and `--logo <path>` (the app's own name
and mark), `--admin-password <value>` (the `admin` module's, 16 characters at
least — generated otherwise), `--yes` (accept every default), `--dry-run` (write
the app, create nothing in your accounts), `--plan` (print the whole run and
write none of it).

[docs/configuration.md](https://github.com/chatfuel-lab/wizard/blob/main/docs/configuration.md)
has the rest of them, and every environment variable, in one place.

## Without a terminal to answer it

`--yes` runs the whole thing without a single question, which needs every answer
on the command line. The `auth` module also needs a Supabase project, so name one:

Pass both as environment variables rather than as flags: a flag's value is in `ps` output and
in your shell history, and an `export` typed at a prompt is in the history too — so in a
terminal, read them from a file or your password manager, and in CI let the runner inject them
as secrets.

Sourcing a file is the shortest form that keeps both out of the history. The file holds
`CHATFUEL_TOKEN=…` (<https://panel.chatfuel.com/integration/auth/token>) and
`SUPABASE_ACCESS_TOKEN=…` (<https://supabase.com/dashboard/account/tokens>) — and a Supabase PAT
has no scopes, it can do everything your account can, so make one for this run and revoke it
afterwards. Keep the file `0600` and out of the repository:

```bash
set -a; . ./secrets.env; set +a      # exported for this shell, typed into no history

npx @chatfuel/wizard --yes \
  --dir ./acme-app \
  --modules livechat,contacts,auth \
  --workspace <id> \
  --supabase-create "Acme app"
```

`--supabase-create <name>` makes the Supabase project, or reuses the one already
called that — so running the same command twice leaves you with one project, not
two. Use `--supabase-project <ref>` instead when the project exists and you know
its ref. Add `--supabase-org <slug>` if the access token can see more than one
organization, and `--supabase-region <code>` to place the project yourself; both
are worked out for you otherwise. The manual alternative, for an account whose
access token you would rather not hand over, is `--supabase-url` +
`--supabase-anon-key`: no Supabase call is made, and the app ships with the SQL
for you to run in the dashboard.

`--app-url <url>` adds the origin the app will be served from to Supabase's
redirect allowlist. `--dry-run` walks the whole run — every question, every
read-only call — and stops short of creating anything in your Chatfuel or
Supabase account: no bot, no project, no trial. The app is still written, which
is the point of it. `--plan` goes one step further and writes nothing at all —
no scaffold directory, no file copied into an embed host, no `.env` or
`.gitignore` line, no lock file and no installed skills afterwards.

## The modules

| Module | What you get |
| --- | --- |
| `livechat` | Operator inbox: conversation list with live updates, per-platform message rendering, composer, takeover. |
| `contacts` | A CRM workspace: record table with saved views, nested AND/OR attribute filters, import and export. |
| `deals` | Board, table and forecast over contacts by sales stage, with drag-and-drop that works on touch. |
| `bookings` | Day/week/month calendar with drag-and-drop, appointments list, staff and working hours. |
| `knowledge-base` | Everything the AI knows about the business: business facts, FAQs, a product catalog. |
| `automations` | The AI's per-scope behaviour: the rules for each channel and entry point, with a test chat. |
| `coworker` | The operator's AI assistant, as a full page and as a dock beside every other module. |
| `flow-builder` | Visual flow editor: canvas, inspector, block and connection editing. |
| `ads-optimization` | Conversion reporting for click-to-WhatsApp ads: which ads each event set covers, and which moments in the chat go back to Meta so it can optimize delivery. |
| `publishing` | Publishing to a connected Instagram account: feed photos, Reels, Stories and carousels, composed against a live preview, published now or queued — with a calendar, retries, and a library of what is already on the account. The scheduling queue needs the deployment's own database; without one, the module still composes and publishes on the spot. |
| `auth` | Sign-in for the people who use the app, on your own Supabase project. Every account that signs up gets a bot of its own in your workspace, and can create more; a teammate can be granted some of the account's bots and not others. This is what turns the app into a product other people can buy. |
| `admin` | The account behind this deployment's own token: every workspace and bot, created, renamed and deleted from inside the app, connected channels, and a health page. Opened by a password in the server environment rather than by any Chatfuel identity, and never in the navigation rail. |

`core` is installed with every one of them: transport and auth, the error
envelope, pagination, the CORS proxy and the traps worth knowing.

## What lands in your project

- A Vite + React + TypeScript app you own outright. Every module is a directory
  under `src/modules/<id>/` that mounts as its own root.
- The design system and the API client vendored as **sources** under
  `src/vendor/` — readable, changeable, no dependency on this package at runtime.
  The API client carries the GraphQL types of the modules you picked and no
  others, which is a small fraction of the full set.
- A dev proxy that keeps your Chatfuel token server-side and relays the
  WebSocket, so the token never reaches the browser.
- `.claude/skills/chatfuel-*/` (Codex: `.agents/skills/chatfuel-*/`) — one skill
  per module, each with the operations, the guides and the playbooks for it, plus
  `chatfuel-update`, which is about the wizard rather than about any module and
  is installed whatever you picked.
- `.env` with your token, written `0600`, and `.env.example` beside it.
- `.chatfuel/lock.json` — what every file in the app was made of: where it came
  from, the digest it had when it landed, and the commit the content was pinned
  to. It is what makes an update possible without a diff.

Then `npm run dev` and it is on <http://localhost:5173>.

## Updating

```bash
npx @chatfuel/wizard@latest update --dry-run   # what a newer wizard would change
npx @chatfuel/wizard@latest update             # do it
```

It reads `.chatfuel/lock.json` and puts every file in one of three states,
decided by digests rather than by a diff: upstream has not moved (skipped),
upstream moved and the file on disk is still the one the wizard wrote
(overwritten), upstream moved and you have edited the file since (left exactly
as it is, reported as a conflict). A file the wizard rewrote on the way in is a
conflict too — the upstream bytes alone would drop the edit that makes the app
run.

Conflicts are the normal outcome, not a failure: they are your work, and the
update does not touch them. It refuses to write into a tree with uncommitted
changes, so `git checkout .` undoes the whole update at once.

Then ask your coding agent to update the app, and the `chatfuel-update` skill
that came with it takes the conflicts from there: it reads the plan as JSON —
with the upstream copy of each conflicting file fetched beside it and the
release notes for the range you are crossing — merges them one at a time, and
tells the wizard which ones it settled with `update --resolved <paths…>`, so the
same conflict is not reported to you again. It is allowed to change those files
and nothing else.

## Deploying

The generated app carries its own deploy command:

```bash
npm run deploy      # Vercel: links, pushes the env, deploys, verifies
```

Or build and run it yourself (`npm run build && npm start`), or use the
`Dockerfile` that comes with it. All three run the same proxy, so the auth gate
and the error codes are identical.
